# 04. 納品の手順（第1.0版）

受託の利益率は「2件目以降をどれだけ流用できるか」で決まる。
この手順は、1件ごとの作り込みを最小にし、資産として残すためのものである。

## 共通の設計方針

1. 人が確認する箇所を必ず作る。AI の出力は「下書き」「推奨」として渡し、送信・確定は人が行う。
2. 顧客が既に使っているツールに寄せる。新しい画面を作るより、スプレッドシートやメールに結果を出す。
3. 入力と出力を1行ずつ記録する。何が入って何が出たかを後から見られるようにする（不具合対応と効果測定の両方に使う）。
4. 秘密情報は顧客のアカウント内に置く。自分の環境に顧客データを溜めない。
5. 設定値（宛先、しきい値、文面）はコードに埋めず、設定ファイルかスプレッドシートに出す。顧客が自分で変えられるようにする。

## 標準の構成

```
顧客の入力元（メール / フォーム / ドライブ / チャット）
    ↓ 取得（定期実行）
処理（Claude API：分類・抽出・下書き生成）
    ↓
確認用の出力先（スプレッドシート / チャット通知 / 下書きフォルダ）
    ↓ 人が確認・修正
確定処理（送信 / 転記 / 保存）
```

定期実行は、顧客環境の都合で次のいずれかを選ぶ。

| 方式 | 向いている場合 | 費用 |
|------|--------------|------|
| Google Apps Script のトリガー | 入出力が Google Workspace 内で完結する | 無料 |
| 小さな常時稼働サーバー（VPS） | メール取得や PDF 処理などライブラリが必要 | 月500〜1,000円 |
| 顧客の PC でタスクスケジューラ | 顧客が社内 PC での実行を希望する | 無料（停止リスクあり） |

## 納品までの流れ（M 規模、2〜4週間）

| 週 | 作業 | 顧客側の作業 |
|----|------|------------|
| 1 | 要件確認（60分）。入力例を10件もらう。出力の形式を決める | 入力例とアカウントの用意 |
| 2 | 構築。入力例10件で精度を確認し、確認欄の設計を決める | 中間確認（30分） |
| 3 | 実データで並行運用（人の作業と並走）。文面・しきい値を調整 | 日次で結果を見る |
| 4 | 操作説明（60分）。手順書を渡す。保守プランの提案 | 検収 |

## 納品物の一覧

- 動くもの（スクリプト、設定ファイル、スプレッドシートのテンプレート）
- 手順書（A4 2〜4枚。起動、停止、設定変更、困ったときの連絡先）
- 入出力の記録場所の説明
- 効果測定の方法（導入前後の作業時間の比較表）

## 効果測定

納品前に、対象作業の時間を1〜2週間、顧客に記録してもらう（1日1行で十分）。
納品後4週間で同じ記録を取り、比較表を作って渡す。
この比較表が、保守契約の継続判断と、次の顧客への事例の両方に使える。

## 2件目以降の流用

納品したコードは、顧客名・設定値を外した形で `recipes/` （本リポジトリの外、自分の管理下）に保存する。
同じ種類の自動化を次に受けるとき、構築工数を半分に見積もり、価格は据え置く。差分が利益になる。

## 品質確認（納品前チェック）

- 入力例10件すべてで期待する出力になるか。
- 誤った入力（空、文字化け、想定外の形式）で止まらず、確認欄に「要確認」と出るか。
- API が応答しないとき、再試行して、それでも駄目なら通知が出るか。
- 秘密情報（API キー、パスワード）がコードやログに書かれていないか。
- 顧客が自分で設定値を変えられるか。手順書だけで変更できるか。
